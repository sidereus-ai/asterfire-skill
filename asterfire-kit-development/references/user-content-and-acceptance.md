# 用户可见文案与开发完成验收

## 用户文案的边界

Kit 概述、`configure.description`、中英文详情、表单名称/标签/说明/校验提示、Demo 名称与说明、输出描述和 `report.md` 都是正式用户界面。默认读者是需要完成任务的领域用户，不要求了解 Kit 开发、容器或平台接口。

- 概述和短描述先说明能解决什么问题、需要提供什么、能得到什么；仅在影响选择时补充适用范围和限制，不把功能介绍写成开发过程或验收纪要。
- 输入说明写清填写内容、文件格式、单位、范围及必要示例；会影响结果的参数解释其含义与取舍。内部 key、函数名、原始配置协议不代替用户说明。高级领域术语可以保留，但需解释使用含义。
- Demo 名称与说明介绍任务场景、示例输入及可学习的用法。实测耗时或指标如确有帮助，须说明对应数据、条件和局限，不能把单个示例得分暗示为所有输入的效果保证。
- 报告解释本次真实结果、关键指标、可视化、结果文件和下一步操作。失败或部分成功时直述用户受影响的结果和可执行处理办法，技术细节留日志。
- 中英文采用同一内容边界。复制模板后必须按真实业务重写展示文案，不把“标准开发结构”“由 Python/CLI 适配”“字段必须与 kwargs 一致”等模板说明直接交付给用户。

以下信息放开发文档、构建/验收记录或日志：镜像/SIF 名称与标签、镜像复用或构建策略、容器路径、`runner`/`@tool_io`/端口 key 对齐、打包命令、调用调试、修复清单、测试通过记录及开发者交接事项。对用户有意义的下载文件名、格式和参数名称可以正常展示。

方法、模型或权重来源、许可/使用限制、资源要求、联网需求以及结果可靠性等会影响用户决策的信息应保留。用“采用何种方法、与用户预期的方法有何差异、如何影响使用”来解释，方法引文放方法说明或参考文献；不能为了简洁隐去真实来源或重要限制。CPU 等资源信息可在适用场景或注意事项中说明，并提示适合的任务规模。

## 开源工具的展示命名

Kit 基于明确的开源工具或项目提供能力时，用户可见名称应保留上游工具的正式名称或通行拼写，搭配简短中文用途，必要时补充 CPU/GPU 等影响选择的运行方式。用户友好不等于删去工具身份，不能只用“结构预测”“数据分析”等泛化功能名替代。使用多个引擎时按实际核心工具命名；不要把未使用的知名项目加入名称。

- 本例使用 `AlphaFold 3 生物分子结构预测（CPU）`，而非仅“生物分子结构预测（CPU）”。采用开放实现和 OpenFold3 转换权重的事实仍在短描述、方法与注意事项中准确说明，不暗示官方版本或官方权重。
- `configure.display_name`、`runner.DISPLAY_NAME`、表单名称、详情页及报告标题应保持一致的工具身份；中英文文案保留同一上游名称。概述或短描述同时说明具体能力，避免只有项目名而没有用途。
- 更新展示名称时保留已发布的稳定 `configure.name`、参数 key 和输出 key，除非任务明确要求迁移这些标识；修改 Kit 内容须升版本。发布后核对平台实际展示名称，不能只检查本地配置。
- 平台名、镜像/SIF 标签、接口契约与开发过程仍属于工程信息，不因保留开源工具名称而重新塞入展示标题。

## 写法示例

以下仅说明文案取舍，不作为任何特定 Kit 能力或效果已获验证的证据；实际使用须与实现和测试结果一致。

不宜作为概述：

> 在 AsterFire 平台使用 OpenFold3 转换权重与 Sergey/Sokrypton 的 AlphaFold 3 开放实现进行 CPU 生物分子结构预测。复用现有 af3-openfold-cpu:1.0.0 SIF，不使用 Google 官方 AF3 权重。

可改为：

> 根据输入的生物分子序列预测三维结构，提供候选结构、置信度评分和可视化报告，帮助比较与评估预测结果。

对应的实现来源和适用限制仍需在方法/注意事项中准确说明。例如在来源已核实时，解释采用第三方开放实现与转换权重、与官方实现存在差异，结果需结合置信度及实验信息评估；镜像标签留开发记录。

不宜放在应用描述：

> 严格声明 tool_io，失败不返回伪结构；已实测某 Demo，3 recycles/2 samples、ipTM=0.91。

可改为：

> 提供可直接载入的示例，帮助了解输入方式和结果解读。分析完成后可查看候选结构、置信度与排名，并下载结构文件和分析报告。

“不伪造结果”由实现和验收保证；置信度较低时，在实际报告中解释该指标及其对结果使用的影响。示例的具体评分仅在有记录支持、标明条件且有助于理解示例时展示。

## 开发完成后的六项验收

每次新建、适配或修改完成后，开发者先测试实际交付版本，再审查用户文案与真实生成的报告。先修复本次授权范围内发现的问题并复测，再提交以下六项总结。总结属于开发交付说明，不能写进面向用户的 `report.md`。

| 序号 | 固定验收问题 | 单选选项 | 通过条件与所需证据 |
| --- | --- | --- | --- |
| 1 | Demo 配置是否完整（GitHub 开源项目还须核对上游官方案例）？ | 完整 / 不完整 | 对照官方 examples/tests/README 与本次支持的功能模式，确认所需参数、真实输入文件、必要资源说明、来源和使用条件齐全；记录覆盖与未覆盖范围，不要求搬入所有上游案例。非 GitHub 项目按实际来源与功能检查，并在证据中说明。 |
| 2 | 交付的 Demo 配置是否能够正常使用？ | 是 / 否 | 用交付配置和引用文件实际运行各 Demo，确认加载/提交参数一致、任务成功且产生有效结果；记录版本、环境、输入、运行标识或日志及结果。仅通过 JSON/文件检查不算通过。 |
| 3 | Kit 描述以及 input 描述是否用户友好？ | 是 / 否 | 逐项审查展示名称、概述、短描述、中英文详情、输入标签/说明/校验提示及 Demo 文案，用户能识别实际开源工具并理解用途、填写方式和主要结果，没有开发过程或接口细节；发布任务还要核对平台实际展示名称，记录审查文件与代表性修改/发现。 |
| 4 | `report.md` 是否面向用户，且不含仅供开发者查看的内容？ | 是 / 否 | 审阅实跑生成的报告（包括已触发的失败分支），确认无部署、接口、自测或调试记录，保留用户需要的方法、结果解释和限制；记录实际报告路径与审查结论。 |
| 5 | 主要结果是否真实、完整且可查看？ | 是 / 否 | 检查实际产物能打开/解析、与输入及运行一致，声明的输出已返回且可访问；报告的表格、图片、结构和下载引用对应真实文件，关键指标有解释，没有占位或伪造结果。平台端到端任务还须检查结果回流与展示。 |
| 6 | 异常输入或运行失败时，是否有清楚提示且不会误报成功？ | 是 / 否 | 结合本次功能实际触发有代表性的非法输入与运行失败，例如缺失文件/格式错误及外部计算失败。确认提示说明问题和用户下一步，状态正确、无伪结果或误导性成功提示，详细错误保留在日志。记录触发条件、状态及提示。 |

单选结论只能使用表中对应的一个选项，不能同时勾选、增加“部分通过/待验证/不适用”或用描述代替选择。第 4 项采用正向问法，使第 2–6 项均为“是”才通过。证据栏独立说明适用范围和验证限制：未完成对应实测/审查、证据不足或受环境限制时，第 1 项选“不完整”，第 2–6 项选“否”，并注明“未验证，按未通过记录”及原因，不得将未验证写成已发现的缺陷。总体通过要求六项均达到通过选项且有对应证据。

测试按用户授权范围执行。本地交付不因本验收自动获得发布或生产计算权限；应完成可做的检查，如实记录平台验证缺口。端到端请求通过 DevOps 完成实际上传、轻量运行和结果回流后再判断，不以模板可见、按钮可点击或代码静态校验替代运行验证。

最终交付说明固定列出六行，列为“序号、验收问题、单选结论、证据/问题与后续动作”。证据引用交付版本对应的文件、实际运行或审查结果；有未通过项时说明缺口与影响，不宣布端到端验收完成。
